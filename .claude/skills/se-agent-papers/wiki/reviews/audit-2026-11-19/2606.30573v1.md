# SWE-INTERACT: Reimagining SWE Benchmarks as User-Driven Long-Horizon Coding Sessions

## Chapters and comparisons

Sections 1–2 and Figures 1–2. The authors manually selected 25 tasks each from SWE-bench Pro, SWE Atlas and DeepSWE for requirements that could be disclosed over several turns. The simulator knows the full prompt, can inspect the workspace and reveals requirements gradually. The original verifier checks final correctness. In the first version, the simulator can read files and history but cannot edit code or run tests. §3, Table 1 and Figure 3. For GPT-5.5, the change is 24.7 − 48.0 = −23.3 percentage points. For Opus 4.8, it is 26.7 − 50.7 = −24.0 points. The same dataset was tested once in single-turn mode and twice more using two different user models. For GPT-5.5, mean cost per attempt rose from $2.78 to $9.84, about 3.54 times the original cost. Section 4, Figures 4–5 and Tables 2–3. A model evaluates requirement coverage using the plan and patches. High coverage can coexist with test failures. Of the labels assigned in an audit of 287 failed runs, 34% indicate a technical error and another 34% a prior requirement the agent missed. About 12% indicate a condition the user did not disclose. A run may receive multiple labels. The effect of the persona on accuracy varies by model. Sections 5–6 situate this metric alongside tests of autonomous implementation.
