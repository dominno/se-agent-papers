# Tangent: An Empirical Study of Testing Practices for LLM-Based Agent Applications

Independent audit on 19 November 2026 • 2608.08413v1 · [Paper record](../../sources/arxiv-2608.08413.md)

## Section-by-section review

- **1–2, Figure 1 and Table 1.** From 1,190 Python repositories using popular frameworks, the authors identified 209 that had agents or tools and also included tests. An initial Gemini-assisted filter identified 3,050 modules. After further filtering and manual review, the annotation sample contained 240 modules from 12 projects and 2,572 methods. Agreement between the two authors before adjudication was κ = 0.92. [PDF, p. 2](https://arxiv.org/pdf/2608.08413v1#page=2) [PDF, p. 3](https://arxiv.org/pdf/2608.08413v1#page=3)
- **3, Figures 2–3.** Test level describes what is being tested. The use of test doubles is a separate dimension. Unit tests of a tool or agent account for 61.8%, interaction tests for 34.6%, multi-tool tests for 3.5% and API calls for 0.1%. Of the labeled methods, 7.5% addressed nonfunctional requirements. Within that group, 49.0% tested security and 33.5% tested performance. Comparisons across frameworks and versions are based on observations of different projects. [PDF, p. 4](https://arxiv.org/pdf/2608.08413v1#page=4) [PDF, p. 5](https://arxiv.org/pdf/2608.08413v1#page=5) [PDF, p. 6](https://arxiv.org/pdf/2608.08413v1#page=6)
- **4, Figure 4 and Table 2.** The 23-pattern taxonomy covers environment setup, data, targets and assertions. Categories can overlap. The study identifies realistic synthetic data in 1,390 methods, simple example data in 1,026 and real data in 39. It finds assertions about agent or tool state in 1,317 methods and about the reasoning trace in 225. For state checks the text reports 51.1%, while the count and table yield 51.21%. [PDF, p. 6](https://arxiv.org/pdf/2608.08413v1#page=6) [PDF, p. 7](https://arxiv.org/pdf/2608.08413v1#page=7) [PDF, p. 8](https://arxiv.org/pdf/2608.08413v1#page=8)
- **5. The complexity of the test.** For each test method alone, the medians are 14 noncomment lines of code and cyclomatic complexity of 1. Including helpers and data setup increases these to 20 and 3. The authors suggest that interaction counts and external state capture another dimension of complexity. [PDF, p. 9](https://arxiv.org/pdf/2608.08413v1#page=9)
- **6, Table 3.** Ten IBM participants with 5–29 years of experience discussed methods, test data, monitoring and nonfunctional requirements. Eight mentioned nonfunctional testing. Here the denominator counts respondents, whereas the 7.5% in the code analysis counts methods. Six participants reported end-to-end testing. [PDF, p. 9](https://arxiv.org/pdf/2608.08413v1#page=9) [PDF, p. 10](https://arxiv.org/pdf/2608.08413v1#page=10)
- **7–10, Table 4 and Figure 5.** The authors distinguish gaps in theory from difficulties adopting known methods and propose research on adequacy criteria, realistic scenarios and observability. Their data cover tests checked into selected Python projects and interviewees from one organization. Filtering may have excluded some methods. The references and data availability statement point to a replication package. - **External supplement, Figures 6–8.** Figure 6 describes the code-analysis model. Figure 7 shows the distribution of assertion types, with equality checks the largest category. Figure 8 compares method-complexity distributions with and without setup and helper functions. The distributions and captions match the medians in Section 5. ## Independent verification

The 12 rows of Table 1 sum to exactly 240 modules and 2,572 methods. Recalculation from Table 2 gives 1,026/2,572 = 39.89% for simple data, 1,317/2,572 = 51.21% for state checks and 225/2,572 = 8.75% for reasoning checks. The rounded distribution of test levels in Section 3 sums to 100%.
